# Versioning, tagging, and changelog policy

**Status:** policy for every release of `@sendust/ts` and its platform packages.
**Applies to:** P16 (candidate assembly), P17 (publication), and every later
release.

## 1. Semantic versioning

Releases follow [Semantic Versioning 2.0.0](https://semver.org/): `MAJOR.MINOR.PATCH`.

- **MAJOR** — a breaking change to the public contract, including any change to
  status semantics, removing or renaming an error code, tightening a cap, or
  lowering a default timeout.
- **MINOR** — additive, backwards-compatible change: a new optional option, a
  new error code, a new platform target, a raised or loosened cap.
- **PATCH** — a fix with no contract change, including security fixes.

The contract is frozen at `0.1.0`. A `0.x` version is not a licence to break it:
while the package is pre-1.0, a breaking change still ships as a major version
with migration notes, exactly as it would after 1.0.

### Pre-releases

| Kind | Version | Tag | Published to |
| --- | --- | --- | --- |
| Release candidate | `X.Y.Z-rc.N` | `vX.Y.Z-rc.N` | npm dist-tag `next` |
| Internal preview | `X.Y.Z-next.N` | `vX.Y.Z-next.N` | never published |
| Stable | `X.Y.Z` | `vX.Y.Z` | npm dist-tag `latest` |

An RC that changes in any way gets a new `N`; a published version is immutable.

## 2. Version source of truth

There is one version number per release, repeated in the files the build and the
two ecosystems need:

| File | Field |
| --- | --- |
| `package.json` | `version` |
| `ts/package.json` | `version` |
| `Cargo.toml` | `[workspace.package] version` |
| `ts/src/index.ts` | `export const version = "…"` |

`scripts/check-versions.mjs` fails when these disagree, when `Cargo.lock` records
a different version for `sendust-core` or `sendust-napi`, or when `CHANGELOG.md`
has no entry for the current version. It runs in `npm run check` and in CI, so a
version bump is one change across those files plus the changelog.

The publish manifest is generated by `npm run prepare:publish`, which pins every
platform package to `ts/package.json`'s version — that pair cannot drift.

## 3. Tags

- Format: `vX.Y.Z` for stable, `vX.Y.Z-rc.N` for a candidate.
- The tag is created only after the release-engineering gate approves the
  candidate, and it must point at the commit the evidence names.
- Never move or delete a tag after publication; publish a new version instead.

## 4. Changelog

`CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
with these categories in this order:

`Added`, `Changed`, `Fixed`, `Security`, `Deprecated`, `Removed`.

Rules:

- The top section is `Unreleased` while a candidate is being assembled.
- On release, move those entries under `## [X.Y.Z] - YYYY-MM-DD`.
- Every user-visible change is listed once, in the category that describes it.
- A security fix says what class of issue was fixed, without exploit detail.
- Entries link to the relevant guide or ADR when behavior is subtle.
- The changelog never claims delivery, retries, pooling, SMTPUTF8, URL
  attachments, or support beyond the matrix in
  [platform validation](../qa/platform-validation.md).

## 5. Compatibility promises

### Runtimes and platforms

Support is exactly what PHASE-14 validated, and nothing broader:

- Node.js 22.23.5 on `linux-x64-gnu`, `linux-arm64-gnu`, `linux-x64-musl`,
  `linux-arm64-musl`, `macos-arm64`, `macos-x64`, `windows-x64` (musl added in
  `1.1.0`).
- Node.js 24.22.3 and 26.13.1: tested at the suite level, not gated for the
  native matrix.
- Bun 1.4.4 and Deno 2.9.8: tarball install, smokes, and the behaviour harness.

A new platform is a minor version; dropping one is a major version. An
unsupported combination keeps failing closed with `CONFIG_NATIVE_UNAVAILABLE`.

### Public API

| Change | Version |
| --- | --- |
| Add an optional option or error code | Minor |
| Add a platform target | Minor |
| Change status semantics, remove or rename a code | Major |
| Change a default timeout or cap downward | Major |
| Raise a hard cap | Major |
| Loosen a cap or add a feature | Minor |
| Fix behavior without a contract change | Patch |
| Security fix | Patch or minor, with an advisory |

The frozen semantics are part of the contract: `accepted` means relay
acceptance, never delivery; `unknown` after DATA is never an automatic retry;
one SMTP transaction runs per session at a time, with concurrent `send()` calls
queued and pooled inside one transport; close is explicit and bounded.

## 6. Not provided, in any version of the MVP

These are non-goals, not roadmap promises: mailbox delivery confirmation, a
persistent queue, a worker process or scheduler, queue adapters, retries beyond
one message's send budget, SMTPUTF8, URL or remote attachments,
provider-specific transports, and plaintext SMTP.

## 7. Release flow

1. Update the four version fields and `CHANGELOG.md` in one change; the version
   check must pass.
2. Assemble the candidate with `npm run assemble:rc` (P16-002): artifacts,
   checksums, dependency inventory, and provenance for the commit.
3. Draft release notes from the changelog (P16-003) and walk the release
   checklist (P16-004).
4. Gate record for P16-005 names the candidate version, commit, and artifact
   hashes. No publish command runs.
5. P17 verifies RC identity, and only then publishes — platform packages first,
   then the facade — with an explicit approval record.
