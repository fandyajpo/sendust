# Sendust 1.0.0

**Released:** 2026-11-19.
**Package:** `@sendust/ts@1.0.0` with `@sendust/ts-<platform>` at the same
version.
**Dist-tag:** `latest` (see the dist-tag note below).

The first stable release. It changes how a transport behaves under load:
concurrent `send()` calls are queued and scheduled instead of being rejected,
one authenticated SMTP session is reused across messages, and only transient
failures are retried. A successful result still means the relay accepted
responsibility, never that a mailbox received the message.

> **Dist-tag note.** The CI publish job hardcoded `--tag next`, so `1.0.0`
> initially landed under `next` while `latest` still pointed at `0.1.0-rc.1`.
> The workflow now reads the tag from `release/<version>/approved.json`, and the
> manual `dist-tag` job moved it: `latest` and `next` both resolve `1.0.0`.

## Installation

```text
npm install @sendust/ts
```

Installing the facade lets npm select the matching platform package through
`optionalDependencies`. No install-time download, compiler, or postinstall script
runs.

## What changed from 0.1.0-rc.1

- **Concurrency.** `send()` is queued. The engine runs up to
  `delivery.maxConcurrent` sends at once (8 by default) over at most
  `delivery.maxConnections` native sessions. A second concurrent `send()` no
  longer throws `TRANSPORT_BUSY`.
- **Session reuse.** After a definitive outcome the session is reset with `RSET`
  and kept, up to `delivery.maxMessagesPerSession` messages or
  `delivery.sessionIdleMs` of inactivity. An error or an `unknown` disposition
  drops it.
- **Bounded retries.** Transient failures — a `4xx` final reply, or a connect,
  operation, or total timeout before `DATA` — are retried with full-jitter
  backoff inside the message's total send budget. `unknown` and `5xx` are never
  retried, and `AUTH_*` stops the transport.
- **Limits and metrics.** The queue is bounded and rejects with
  `LIMIT_QUEUE_FULL`; `transport.stats` reports queue depth, active sends,
  connections, concurrency, and outcome counters.
- **Session lifetime.** A transport holds one session open until `close()`, which
  sends `QUIT` and settles anything still queued with `TRANSPORT_CLOSED`.

The semantic contract is otherwise unchanged: `accepted` requires a positive
final `DATA` reply, `unknown` is final, and one SMTP transaction runs per session
at a time.

## Upgrade notes

`TRANSPORT_BUSY` is no longer produced by the facade; the native layer still has
it, and it is not reachable through the public API. Code that relied on catching
`TRANSPORT_BUSY` to implement its own queue can drop that queue.

`SmtpTransport` is no longer `Clone`, because it owns a live session.

## Known limitations

- The benchmark is loopback only, one machine, one runtime, and the relay shares
  a process with the client; it is a relative comparison, not a provider
  measurement.
- Sendust's concurrency ceiling is 32; the 50- and 100-way workloads in the
  original plan run at 32 for both clients so the comparison stays fair.
- Sendust re-established a few sessions in the benchmark (4 connections for 320
  sequential messages). The cause is not yet established and is recorded rather
  than hidden.
- Provider-specific quotas are not modeled: SMTP does not advertise them, and
  guessing them would break the "no fabricated limits" rule.
