# Sendust 1.2.0

**Released:** pending — prepared 2026-11-23, from the CI `publish` job over OIDC,
tag `v1.2.0`.
**Package:** `@sendust/ts@1.2.0` with `@sendust/ts-<platform>` at the same
version.
**Dist-tag:** `latest`.

DKIM signing. Optional: a caller who does not set `dkim` sends byte-identical
messages to `1.1.1`.

## Installation

```text
npm install @sendust/ts
```

## What changed

- **DKIM signing (RFC 6376).** `dkim: { domain, selector, privateKey, headers? }`
  signs every message before it reaches the relay ([ADR-0024](../architecture/decisions/0024-dkim-signing.md)):

  ```ts
  const transport = createTransport({
    host: "smtp.example.test",
    port: 587,
    secure: "starttls",
    auth: { user: "sender@example.test", pass: process.env.SMTP_PASSWORD },
    dkim: {
      domain: "example.test",
      selector: "sendust",
      privateKey: process.env.DKIM_PRIVATE_KEY,
    },
  });
  ```

  The core canonicalizes and signs the bytes it composed — `rsa-sha256`,
  relaxed/relaxed — and prepends one `DKIM-Signature` field, so what the
  transport sends is what was signed and the wire cap covers the signature. The
  body is hashed in full (no `l=` tag), `From` is always covered, a field the
  message does not carry is skipped, and a field RFC 6376 forbids signing (`Bcc`,
  `Received`, `Return-Path`, …) is rejected.
- **A new error code, `CONFIG_INVALID_DKIM_KEY`.** The PEM key (PKCS#1 or
  PKCS#8, 1024–4096 bits) is parsed when the transport is created, so an unusable
  key fails `createTransport` instead of failing after `DATA`.
- **Two pinned dependencies**, `rsa` 0.9.10 and `sha2` 0.10.9, both RustCrypto
  and `MIT OR Apache-2.0`
  ([dependency policy](../engineering/dependency-policy.md)).

The SMTP engine, the delivery engine, the caps, the timeouts and the result model
are unchanged.

## Known limitations

- Only `rsa-sha256` with relaxed/relaxed canonicalization. Ed25519
  (`ed25519-sha256`), multiple signatures, and the `i=`/`q=`/`l=` tags are not
  implemented.
- Sendust publishes no DNS record and stores no key. A selector whose DNS record
  does not match still reaches the relay, and the send is still reported
  `accepted`: relays accept by envelope, so deliverability is not observable from
  here.
- Nothing about the signature is exposed in `SendResult`; signing either succeeds
  or the send fails before the relay is contacted.

## Upgrade notes

Drop-in for `1.1.1`. Nothing to change unless you want to sign, in which case add
`dkim` with the key your DNS `_domainkey` record already publishes.
