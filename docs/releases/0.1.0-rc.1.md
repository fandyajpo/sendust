# Sendust 0.1.0-rc.1 — release notes draft

**Status:** draft for the first release candidate. Nothing is published; the
publication decision is P17. This is the release-notes input for P16-005.

## Summary

Sendust is a standalone native email delivery engine for Node.js, Bun, and Deno.
It submits one message per `send()` call through an SMTP relay you configure, and
reports what the relay did — never that a mailbox received the message.

The 0.1.0 candidate is the MVP: a Rust core with a Node-API 8 binding and a
narrow, runtime-neutral TypeScript facade, packaged for five native targets.

## Installation

The package is pre-release and not on the registry yet. From a checkout:

```text
npm ci
npm run build:native
npm run build --workspace ts
npm run prepare:publish
npm install ./artifacts/publish/sendust-ts-0.1.0-rc.1.tgz
```

A published release installs the facade and lets npm select the matching
platform package through `optionalDependencies`. No install-time download,
compiler, or postinstall script runs.

## Semantic contract

- **`accepted`** — the relay took responsibility for the message. Not a delivery
  confirmation; there is no `delivered`, `opened`, `bounced`, or `queued` status.
- **`rejected`** — an explicit negative final reply; nothing was accepted.
- **`unknown`** — the body was transmitted but the final reply was not observed.
  The relay may have accepted it. Sendust never resends; retry is a caller
  decision that requires application-level idempotency.
- **`TRANSPORT_BUSY`** — one send is already active; no connection is opened and
  nothing is queued.
- **`TRANSPORT_CLOSED`** — the transport is closing or closed.
- **Recipients** — each `RCPT` outcome is preserved; a recipient is `accepted`
  only after a final `DATA` 2xx, and an accepted subset gets one shared `DATA`.

Details: [quick start](../guides/quick-start.md) and
[errors and operations](../guides/errors-security-operations.md).

## Lifecycle, timeouts, and caps

- `open -> closing -> closed`; close is explicit, idempotent, and bounded by
  125 s; no GC-dependent shutdown.
- Timeouts: connect 10 s, operation 30 s, total 120 s, close 125 s — finite and
  lower-only.
- Caps: 100 recipients, 10 MiB per attachment, 20 MiB aggregate raw, 30 MiB wire.

Details: [lifecycle and limits](../guides/lifecycle-limits.md).

## Attachments

Buffer attachments are always allowed within the caps. Path attachments require
`attachments.allowFileAccess: true` and read bounded regular files only. There is
no URL, stream, or remote attachment form.
Details: [addresses, MIME, and attachments](../guides/addressing-mime-attachments.md).

## TLS and security

- TLS 1.2 or newer with certificate and hostname verification against the
  bundled public roots. No plaintext mode, and no way to disable verification.
- `tlsRootCertificate` adds anchors to the trust store; it cannot remove roots
  or weaken verification.
- Errors, messages, and logs exclude credentials, bodies, attachment bytes, and
  absolute paths.

## Known limitations and non-goals

- No mailbox delivery confirmation.
- No automatic retry, connection pool, internal queue, worker, or scheduler.
- No SMTPUTF8: envelope local parts must be ASCII.
- No URL or remote attachments.
- macOS code signing and notarization are not part of the MVP.
- Only the five targets above are claimed; anything else fails at
  `createTransport` with `CONFIG_NATIVE_UNAVAILABLE`.

## Migration notes

This is the first release, so there is no migration. Future breaking changes to
status semantics, error codes, defaults, or caps follow the
[versioning policy](../engineering/versioning-policy.md): a major version with
migration notes.
