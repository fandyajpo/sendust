# Sendust 1.0.1

**Released:** 2026-11-21, from the CI `publish` job, tag `v1.0.1`.
**Package:** `@sendust/ts@1.0.1` with `@sendust/ts-<platform>` at the same
version.
**Dist-tag:** `latest`.

A performance fix. No API, result, error code, option, or limit changed.

## Installation

```text
npm install @sendust/ts
```

## What changed

- **The pool fills to the work waiting.** Concurrency used to grow one slot per
  eight consecutive successes, so a burst spent most of its run
  under-provisioned and messages queued behind each other. It now rises to
  `min(maxConcurrent, active + queued)` before each scheduling pass. Throttling
  still halves the level and holds a cooldown, so a relay that pushes back is
  still obeyed.
- **One fewer round trip per message.** `RSET` is sent only when an envelope was
  left open — every recipient refused, or `DATA` refused — instead of after every
  completed transaction. A session that received `421` is never reused.

Why: a 100-message run at concurrency 5 against Gmail measured a p95 of 11.9 s
against Nodemailer's 5.3 s, with throughput within 7%. The tail was queue wait,
not per-message work. Full analysis: [real-relay optimization](../qa/real-relay-optimization.md).

## Known limitations

- The Gmail comparison has **not** been re-run against `1.0.1`; the expected
  improvement is a projection in the analysis, not a measurement.
- At concurrency 5 both clients sit near the relay's ceiling (~4 s per message on
  Gmail), so throughput gains are bounded by concurrency, not by client work.
- Sendust caps concurrency at 32 by design.
- Provider quotas are still not modelled; only observed pushback is.

## Upgrade notes

Drop-in for `1.0.0`. If you were compensating for the old ramp by creating
several transports, one transport is enough now.
