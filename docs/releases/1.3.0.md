# Sendust 1.3.0

**Released:** 2026-11-24, from the CI `publish` job over OIDC, tag `v1.3.0`.
**Package:** `@sendust/ts@1.3.0` with `@sendust/ts-<platform>` at the same
version.
**Dist-tag:** `latest`.

The fixes from the source audit of `1.2.1`, and one additive state. A caller who
neither reads `transport.state` nor sets `delivery.sessionIdleMs: 0` sees no API
change, and the wire changes only where the relay advertises `SIZE`.

## Installation

```text
npm install @sendust/ts
```

## What changed

### A stopped transport says so

- **`transport.state` and `stats.state` report `failed`.** A rejected or
  unsupported credential stops the engine, which is right — bad credentials do
  not heal by waiting — but the state still read `"open"`, so a health check
  keyed on it reported healthy while every send failed.
- **A later send names the cause.** It rejects with `AUTH_FAILED` (or
  `AUTH_UNSUPPORTED`) and dials nothing. It used to reject with
  `TRANSPORT_CLOSED`, which suggests a transport that is merely shutting down.
- **There is no in-process reset.** A credential rotation builds a new
  transport, and the session a failed engine can never reuse is closed as its
  send settles rather than held open until `close()`.
- **`close()` still works** on a failed transport, and settles `"closed"`.

`"failed"` is additive to the published union: nothing that read `"open"`,
`"closing"` or `"closed"` changes. A caller with an exhaustive `switch` gains a
branch to handle.

### The wire, where `SIZE` is advertised

- **`MAIL FROM` declares `SIZE=<n>`** when the relay advertises the extension
  (RFC 1870).
- **A message above the relay's own limit fails locally**, with
  `LIMIT_WIRE_BYTES` and `stage: "mail"`, before the envelope opens. Being
  disconnected mid-`DATA` is the failure this prevents, and that failure is
  reported as `unknown`, which forces a human to decide whether to resend.

A relay that never advertises `SIZE` sees exactly the commands `1.2.1` sent.

### Long bearer tokens

An `AUTH` line was held to the 512-octet command line, so an XOAUTH2 token from
Microsoft 365 or Google Workspace failed with `VALIDATION_HEADER_INJECTION` — a
code that accuses the caller of injecting a command. `AUTH` and its challenge
responses now use the response bound their own validator already enforced, up to
1,228 octets as RFC 4954 requires of servers, and an over-long value is
`VALIDATION_INVALID_OPTION`.

### Six wrapper fixes

- **An abnormal task end is `INTERNAL`, not `TRANSPORT_BUSY`.** A send whose
  task ended abnormally left a transport that answered `TRANSPORT_BUSY` for the
  life of the process, with the wrong cause.
- **A pooled session is released once.** When the native result failed mapping,
  the session was released twice: two sends could then run on one session.
- **The `RSET` reply is checked.** A session is reused only after the relay
  answers the `RSET` that closes the transaction with a positive reply, as
  ADR-0022 says; any other reply drops it.
- **Cancellation cannot inherit the previous message.** The stage and recipients
  are reset before composition, so an abort during composition cannot report the
  previous message's recipients as `unknown`.
- **`sessionIdleMs: 0` means no idle reuse on both sides.** The engine pooled a
  session the core then refused, so the two disagreed about zero.
- **`host` rejects embedded whitespace** with `CONFIG_INVALID_RELAY`, as the
  documented contract says, rather than failing later as a connection reset.

### The suite that found them

- **The binding is tested on every claimed Node.js version** — 22.23.5, 24.22.3
  and 26.13.1 — instead of one.
- **`tsc` type-checks the whole test suite**, not two of seven files.
- **The audit is committed** under `audit/code-audit/`: six documents, two HIGH,
  13 MEDIUM, 15 LOW and 10 INFORMATIONAL findings, from a static review.

## Known limitations

- Unchanged from `1.2.1`: only `rsa-sha256` with relaxed/relaxed
  canonicalization, no Ed25519, no multiple signatures, and Sendust still
  publishes no DNS record.
- The audit's delete-or-wire items are decisions, not fixes: the core's unused
  lifecycle module, `validate_in_order`, the two unproducible error details and
  `PROTOCOL_REJECTED` are still present. They are recorded in
  `audit/code-audit/IMPROVEMENT_ROADMAP.md` §1.3 and §3.
- A failed transport has no reset. Rebuilding it is the recovery, and the caller
  owns the new credential.

## Upgrade notes

Drop-in for `1.2.1`, except that `transport.state` may now be `"failed"`: handle
it if you branch on every state, and rebuild the transport rather than retrying on
it.
